# Идеи по ускорению VK-парсера (без реализации)

## Контекст

Ускорение `parser-service` (VK-адаптер). Это список вариантов на выбор, ничего из этого пока не
реализовано.

Текущее узкое место и то, что уже поддерживает архитектура:

- Реальный парсинг (`app/adapters/vk.py`) — синхронный Playwright, один браузер/контекст/страница
  на задачу. Самое дорогое место — `_has_external_site`: для КАЖДОГО кандидата отдельный
  `page.goto` на страницу группы + ожидание селектора (до `VK_SITE_CHECK_TIMEOUT_MS`=4с),
  строго последовательно, один за другим.
- Скролл выдачи (`_scroll_until_enough_new_candidates`) ждёт фиксированные `_SCROLL_WAIT_MS`=1500мс
  на каждой попытке, независимо от того, дозагрузилось ли уже содержимое.
- Задача парсинга запускается через `BackgroundTasks` (`routers/parse.py`) → sync-функция уходит в
  threadpool Starlette. Ничего не мешает нескольким задачам работать одновременно в одном процессе.
- `data-service` (`crud/accounts.py: next_available()`) **уже** поддерживает пул из нескольких VK-
  аккаунтов с реальной row-level блокировкой (`with_for_update(skip_locked=True)`) — конкурентные
  вызовы получают РАЗНЫЕ аккаунты, есть даже тест на эту конкурентность. Orchestrator тоже не
  сериализует разные кампании между собой.
- Во всём проекте (parser-service, messaging-service, data-service) нет ни одного обращения к
  официальному VK API (`api.vk.com`) и нет поля с access-токеном у аккаунта — везде чистая браузерная
  автоматизация через cookie-сессию (`storage_state`). Похоже, это осознанный выбор (меньше похоже
  на бота, не нужна регистрация приложения/токена) — это важно учитывать в идеях ниже.

Весь код `vk.py` изобилует комментариями "проверено вживую" — значит любые изменения тайминга
или сети нужно будет так же проверять вживую перед мержем, это не чисто юнит-тестируемая логика.

## Варианты, от наибольшего ожидаемого эффекта к меньшему

### 1. Резать вес страниц (блокировка ресурсов) — высокий эффект, низкий риск — РЕАЛИЗОВАНО 2026-08-24
Через `context.route()` блокируем картинки/шрифты/медиа (по `resource_type`) и известные домены
сторонней аналитики/трекеров (Google Analytics, GTM, Яндекс.Метрика, Mail.ru, doubleclick) — белым
списком того, что режем, а не чёрным того, что оставляем. Применено на весь `BrowserContext` разом
(`_block_heavy_resources` в `adapters/vk.py`) — покрывает и `_FEED_URL`, и каждую страницу группы в
`_has_external_site`, и `check_session`, одним вызовом сразу после `new_context()`. JS/CSS самого VK
не трогаем — это SPA, без его скриптов ничего не отрисуется.
Проверено вживую 2026-08-24 (`VK_HEADLESS=false`, реальный аккаунт): два тестовых запуска через
`POST /parse` — карточки выдачи (`_GROUP_CARD_SELECTOR`) и поле сайта у группы (`_SITE_FIELD_SELECTOR`)
по-прежнему появляются и корректно читаются с блокировкой включённой (второй прогон, свежее ключевое
слово без дедупа: found=5/inserted=5 из 9 проверенных кандидатов, без ошибок и капчи).

### 2. Параллельные проверки сайта у кандидатов — высокий эффект, средний/высокий риск
Сейчас `_has_external_site` строго последовательна. Открыть N дополнительных вкладок в том же
браузерном контексте и проверять несколько кандидатов одновременно (например, 2–4 одновременно)
вместо одного за другим. Технически потребует перехода этого куска на `async_playwright` (текущий
sync API плохо параллелится по вкладкам) — `search_communities` наружу останется синхронным методом,
внутри — свой `asyncio.run()`/`gather` в отдельном потоке.
Главный риск — это самое заметное поведенческое отличие: несколько одновременных запросов с одного
аккаунта выглядят менее "по-человечески" и повышают шанс поймать троттлинг/капчу (в конфиге уже есть
комментарий про пойманный мягкий троттлинг VK на **последовательных** запросах). Стоит делать
настраиваемым (например, `VK_SITE_CHECK_CONCURRENCY`, по умолчанию консервативно — 2) и обязательно
проверять вживую перед тем, как поднимать значение.

### 3. Слушать сетевой ответ вместо ожидания DOM-селектора — потенциально высокий эффект, требует разведки
Вместо `page.goto` + `wait_for_selector(_SITE_FIELD_SELECTOR)` — подписаться на `page.on("response")`
и поймать внутренний JSON-запрос, которым VK подгружает данные о сообществе (там наверняка есть поле
сайта), не дожидаясь полной отрисовки блока в DOM. Может быть быстрее, чем ждать рендер конкретного
CSS-селектора.
Это идея, а не факт — нужно вживую посмотреть Network-таб на странице группы VK и найти реальный
эндпоинт/форму ответа, прежде чем закладывать её в реализацию. Отдельный спайк перед кодом.

### 4. Адаптивное ожидание скролла вместо фиксированной паузы — средний эффект, низкий риск
Сейчас каждая попытка скролла ждёт ровно `_SCROLL_WAIT_MS`=1500мс. Заменить на поллинг роста DOM
короткими интервалами (например, каждые 200–300мс) с тем же общим потолком — досрочный выход, как
только карточки дозагрузились, вместо гарантированного ожидания полных 1.5с на каждой итерации.
Не меняет сетевое поведение/паттерн запросов — риск минимальный, чисто механическая правка.

### 5. Тёплый браузер на аккаунт вместо запуска с нуля каждый раз — небольшой эффект, средний по сложности
Сейчас каждая задача — новый `chromium.launch()` + `new_context()` + закрытие в конце (холодный
старт браузера каждый раз). Если держать браузер живым между задачами на один и тот же аккаунт (пока
он не в cooldown), экономим время запуска/остановки на последующих запусках.
Стоит своей сложности: нужно управлять жизненным циклом простаивающих браузеров (закрытие по
таймауту, обработка падений процесса) — выигрыш умеренный, а инфраструктурного риска добавляет
заметно больше, чем пункты 1 и 4.

### 6. Параллельные кампании на разных аккаунтах — эффект зависит от размера пула, риска в коде нет
Это не правка в `vk.py` вообще: `data-service` и orchestrator уже умеют раздавать разные VK-аккаунты
конкурентным задачам и не сериализуют разные кампании. Если в пуле реально больше одного активного
VK-аккаунта — throughput уже можно поднять просто запуская несколько кампаний параллельно, без единой
строчки изменений в парсере. Если аккаунт по факту один — этот рычаг не работает, тогда ускорение
может дать только сам код (пункты 1–4).
**Стоит уточнить, сколько сейчас реально активных VK-аккаунтов в пуле** — это прямо определяет,
насколько ценен этот вариант.

### 7. Официальный VK API вместо браузера для проверки сайта — самый большой потенциальный эффект, но архитектурный сдвиг
`groups.getById` с `fields=site` умеет отдавать до 500 групп за один HTTP-запрос. Один такой вызов
вместо десятков/сотен последовательных браузерных переходов — теоретически самый большой выигрыш по
времени среди всех вариантов.
НО: у аккаунтов сейчас нет access-токена вообще (только `storage_state` cookies), и нигде в проекте
API VK не используется — похоже на осознанное решение (детектируемость / не нужна регистрация
приложения). Это подняло бы вопрос политики проекта, а не просто скорости, поэтому не может быть
"тихой" оптимизацией — нужно отдельное решение, стоит ли вообще идти в эту сторону.

## Открытые вопросы (для решения перед реализацией любого пункта)

- Сколько сейчас реально активных VK-аккаунтов в пуле — влияет на ценность варианта 6.
- Стоит ли вообще рассматривать официальный VK API (вариант 7) или это сознательно избегается из
  соображений детектируемости/политики VK.
- Какой уровень риска (капча/троттлинг) приемлем ради скорости — определяет, стоит ли вообще трогать
  вариант 2 (параллельные вкладки) или ограничиться низкорисковыми 1 и 4.

## Верификация (когда дойдёт до реализации любого из пунктов)

- Прогон существующих тестов `parser-service/tests/` (`pytest`) — не должны сломаться дедуп/статусы.
- Live-проверка на реальном VK-аккаунте в headed-режиме (`VK_HEADLESS=false`) на 1–2 кампаниях —
  как и все существующие правки в `vk.py`, тайминги и селекторы этого файла проверяются вживую, а не
  только юнит-тестами.
